<h2>池的稳定性，来自「及时发现与及时替换」</h2>
<p>池里几十条地址，总会有几条出问题。稳定的池不是「没有坏地址」，而是「坏地址能被快速发现并换掉」。这两件事分别对应监控与更换。</p>
<p>所以提升稳定性的重点不在技术优化，而在运维流程。流程没建立，池越大越乱。</p>

<h2>三个动作：监控、剔除、补充</h2>
<p>监控：周期性检查每个地址是否可用、延迟是否正常。剔除：连续失败的地址自动或手动摘除，不再分配给使用者。补充：把修好的地址放回，或者采购新地址补足数量。</p>
<p>三个动作形成闭环。缺任何一个，池都会逐渐退化：只有监控没有剔除，坏地址仍在被分配；只有剔除没有补充，池会越用越小。</p>

<h2>监控看什么指标</h2>
<p>三个指标够用：连通性（能否连上）、延迟（大致水平）、失败次数（连续失败计数）。</p>
<p>不必追求精细。很多团队做了一堆报表，最后只看一个数：可用率。可用率低于某条线就介入，这个简单规则比复杂报表更有效。</p>

<h2>剔除规则怎么定</h2>
<p>常见的规则是「连续三次失败摘除」。三次能过滤掉偶发抖动，又不至于让问题地址服务太久。</p>
<p>摘除后要标记状态与时间，不要直接删除记录。删掉之后就不知道这条地址为什么被摘，也无法判断是否该重新启用。</p>

<h2>更换的时机</h2>
<p>三种时候该换：连续不可用且修复无望；延迟长期高于池内平均一大截；地址出现明显的历史痕迹（访问时频繁被要求验证）。</p>
<p>第四种是「同段影响」——某条地址表现突然变差，而池内其他地址正常。这种情况先观察，多数会自愈；持续超过一天再考虑换。</p>

<h2>冷却期为什么必要</h2>
<p>地址回收后立刻给别人用，前一位使用者留下的痕迹会直接继承。这在外部看来就是「新账号带着旧记录」，是很多莫名异常的来源。</p>
<p>冷却时长没有统一标准，几天到几周都有人用。原则是「重要账号用冷却久的地址」，次要用途可以短一些。</p>

<h2>负载均衡能提升稳定性吗</h2>
<p>能提升一部分，但要理解它解决的是什么。负载均衡解决「单条地址被跑满」，不解决「这条地址本身不可用」。</p>
<p>所以负载均衡要建立在「地址池状态清楚」的基础上。池里一半是不可用地址，再均衡也没有意义。</p>

<h2>三个常见误区</h2>
<p>一是以为地址越多越稳。地址多但没人维护，坏地址比例会上升。二是以为换得越勤越好。频繁换会破坏地址稳定性，也让记录难以维护。</p>
<p>三是以为技术能解决全部。池的稳定性更多取决于记录与流程，而不是用了什么软件。</p>

<h2>把「可用率」当成唯一要看的数</h2>
<p>指标多了反而没人看。建议只盯一个数：池内可用地址占比。这个数下降，说明要么坏地址变多，要么补充没跟上，两种都需要立刻动手。</p>
<p>可用率不需要精确到小数点后两位，按天看趋势就够。连续三天下降就该介入，而不是等到用户抱怨才想起来检查。</p>
<h2>常见问答</h2>
<h3>池越大越稳定吗？</h3>
<p><strong>答：</strong>不一定。规模大了，维护成本与坏地址比例都会上升。</p>
<h3>多久检查一次？</h3>
<p><strong>答：</strong>五到十分钟一次足够。太频繁会增加线路负担。</p>
<h3>坏地址能修复吗？</h3>
<p><strong>答：</strong>多数不能。暂不可用可能是临时故障，长期不行的建议直接替换。</p>
<h3>怎么判断该不该换？</h3>
<p><strong>答：</strong>看是否长期低于池内平均水平，以及是否出现明显的历史痕迹。</p>
